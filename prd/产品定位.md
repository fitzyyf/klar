# 改动星云 · 产品定位

## 一句话

给 AI agent 会话的提交闸口：按「这一回合让它做什么」，看「它的改动碰到了哪些全链」，看懂了，再让它自己提交。

## 需求原话

从最初的几轮对话里整理，按先后：

1. VibeCoding、SpecCoding 里代码评审很重要。每次看行数、看 +/- 没有意义，没人能快速看出为什么这样改、改了啥。
2. 想要的是对象调用链：在调用链上标出改动点，点进去看具体函数，哪些是加的、哪些是删的，并且有历史记录。
3. 每条线是一条全链路。改了某处代码，就找出经过它的全链，标出改了的调用点。像星云图。
4. 有变动的要高亮，动画要考虑。可以是桌面，也可以是 TUI。
5. 要考虑性能、基准，以及多个 agent 会话同时改时怎么分清。
6. git 的提交只是参照。
7. 重点：和 agent 的会话交互，不是 git diff 机制。评审通过后，让 agent 去提交。

## 要解决的问题

一个人同时开几个 agent（Claude、Codex、Grok），在同一个仓库里并行干活。到了收尾，现有的办法都不够：

| 现在的做法 | 缺什么 |
| --- | --- |
| `git diff` / PR 按文件看行 | 几个会话和人自己的改动混在同一个工作区，分不清谁改的；按文件排，看不出调用关系；看不到为什么改 |
| IDE 里 agent 的逐块接受 | 只在一个会话里，按行接受；看不出改一个方法连带影响了哪些入口 |
| AI 评审机器人 | 用 AI 评 AI，结论还要人再读一遍；它评的还是 diff |
| IDE 的调用层级 | 能看调用关系，但不知道哪些是这次改的 |

所以真正缺的是三样东西连在一起：**谁改的**（归属到会话）、**为什么改**（这一回合的指令）、**改动波及到哪**（全链）。

## 定位

改动星云是评审时「看懂」的工具，加一个给 agent 收尾的闸口。

- 改动的来源是 agent 会话记录里的写文件工具调用，不是 `git diff`。所以几个会话并行时，每个会话只看到它自己写的。
- 看的单位是回合：你的一条指令，到下一条指令之间 agent 做的事。
- 看的形状是全链：从入口（页面、定时任务、接口）到叶子（数据库、外部服务），经过这回合改过的方法或调用。
- 结论只有两个：通过、退回。工具自己不跑 git，也不跑 tmux，不碰任何 agent 进程；它把要交回的那句话写好，由人粘给 agent。

## 不做什么

- 不做 git 客户端，不暂存、不提交、不推送。
- 不做 AI 评审，不替人下结论。界面上的每一句说明都来自解析结果，不是模型写的。
- 不跑测试、不跑构建。
- 不管人自己手改的文件。它们不在任何会话记录里。

## 给谁用

同时驱动多个 agent 写代码的开发者或技术负责人。本机并行开着 Claude、Codex、Grok 的会话，仓库以 Java + Vue 为主，也有 TypeScript、Python、Go。

## 三个场景

1. **一个会话收尾。** 看每个回合碰到的全链，确认影响面符合预期，记下通过，把那句话粘回 agent，它自己提交。
2. **几个会话并行。** 两个会话都改了同一个文件。切换会话，各看各的编辑和各自的全链，不会混在一起。
3. **对照指令和自述。** 你说的是什么，agent 说它做了什么，全链显示它实际碰了什么，三样放在一起。原型 14:02 那一回合里，agent 说「支付改到发货时再扣」，但全链里只有被拆掉的支付，没有新接上的。这类出入是按行看 diff 很难发现的。

## 核心概念

| 词 | 意思 |
| --- | --- |
| 会话 | 三家记录里一个在这个仓库工作过的 agent 会话 |
| 回合 | 一条人发的指令到下一条之间 |
| 编辑 | 回合里一次成功的写文件工具调用 |
| 星 | 一个方法、入口或叶子 |
| 跳 | 一次调用，从一颗星到另一颗 |
| 全链 | 从入口到叶子、经过本回合改动的一串跳。实线是回合结束时的，虚线是这回合拆掉的 |
| 参照 | 绑上会话时的 `HEAD`，只写给人和 agent，不用来找改动 |

## 评审流程

1. 顶栏选会话。
2. 左边从最新的回合往回看。中间上方是你说的、它说的；星云是实际碰到的全链。
3. 点全链、点跳、点星，右边看函数体加上和删掉的行、调用的前后。
4. 看完整个会话，点「记下通过」或「记下退回」。界面给出要交回这个会话的那句话，复制下来，粘回 agent 那边。

## 价值

- **从读行到看链。** 改动按调用关系摆出来，入口到叶子一眼看完，不用在文件之间跳。
- **看见连带影响。** 原型里改的是下单，但每晚对账也经过被改的库存预占，这条线会自己出现。
- **归属清楚。** 并行会话互不干扰，不用人去猜哪行是谁写的。
- **提交权在人。** agent 只在人点过通过之后才提交，提交说明和参照都写在那句要粘回去的话里；粘不粘、粘给谁，也是人定的。

## 先做什么

第一版：

- 会话来源：Claude、Codex、Grok 三家的会话记录。
- 语言：Java、TypeScript / Vue、Python。Go 放第二版。
- 界面：桌面客户端。
- 结论：通过、退回。
- 历史：每个会话的回合，和每次评审的结论。

以后：

- 跨端接线：Vue 页面里请求的 URL 接到 Java Controller 的 `@RequestMapping`，页面到数据库连成一条全链。
- 按全链记「已看过」，评审进度可见。
- 会话之间的冲突提示：两个会话改了同一个方法时在顶栏标出。

## 怎么算做成了

- 一个会话从打开到给出结论的时间。
- 退回里有多少是看全链才发现的（连带影响、指令和实际不符）。
- 通过之后 agent 提交成功的比例。
